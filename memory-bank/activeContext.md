# Active Context

Current focus: BMChat is now an e-mail-first messenger that uses the user's VPS at `5.187.4.132` only for the invite landing page (`/i`), the Android update manifest+APK (`/update.json`, `/apk/`), and the Desktop update manifest (`/desktop-update.json`). All actual conversation traffic — including the new e-mail invitations and their auto-acceptance on the receiving side — flows over the user's own IMAP/SMTP server, fully encrypted via Autocrypt-driven SecureJoin. The Rust core (Rust 1.91.1, Android NDK r25c) generates invite links that point at `http://5.187.4.132/i#…`; the placeholder `i.bmchat.example` is retired and legacy hosts (`i.bmchat.example`, `i.delta.chat`) are still accepted on parse for back-compat. The in-app Android updater (`BMChatUpdater`) pulls `update.json`, verifies the SHA-256 of the downloaded APK, and installs it via `PackageInstaller`. The Electron main process now runs an analogous `bmchat-updater.ts` that polls `desktop-update.json` and offers a download dialog. Cleartext HTTP is whitelisted only for the VPS IP. The earlier UI guard layer in Java/TypeScript/Swift remains as a safety net for legacy QR codes generated by older builds.

Recent decisions:
- Start with all three clients: desktop, Android, and iOS.
- Treat licensing as unresolved for commercial/closed distribution; default to GPL-compatible open fork for desktop and Android.
- Keep upstream mergeability as a primary engineering constraint.
- Create project documentation before deep code modifications.
- Keep core submodules upstream-clean unless a proven user-facing requirement needs a controlled change.
- Use `BMChat` as the normal UI name and `BroMoreChat` for long-form product/marketing contexts.
- Treat "common chats" as existing Delta Chat group chats in this phase; no public Telegram-like communities are implemented yet.
- BMChat design direction is now `Burgundy Tech + friendly messenger` based on `brand/assets/bmcha-logo-source.jpeg`.
- Android manual testing exposed a startup-crash issue in the first rebuilt APKs: Gradle packaging ran without `libnative-utils.so`. The test APKs were repaired by restoring native libraries for all supported ABIs from the official Delta Chat `2.49.0` APK and rebuilding.
- Empty endpoint values in `brand/config/bmchat-brand.json` mean the corresponding Delta/upstream integration must be disabled, not used as a fallback.
- BMChat keeps manual IMAP/SMTP login for arbitrary mail servers, but incoming classic emails without `Chat-Version` or a known BMChat/Delta thread are tombstoned and do not create chats/notifications.
- The Show Classic Emails UI is hidden in desktop, Android, and iOS; existing profiles are migrated to `show_emails=0`.
- The onboarding logo, the welcome backdrop, the tray/launcher icons, and the About dialog were re-rendered to match the BMChat burgundy "B" identity. The default chat onboarding string was rewritten to "Свободный чат через вашу почту" / "Free chat through your email".
- Donation surfaces were removed from the Settings screens, menus, device update messages, metainfo, and stock translations across desktop, Android, and iOS. The core no longer sends a recurring donation device message; `donation_request_maybe` is now a no-op that just disables future checks.
- All references to delta.chat, transifex, and Delta Chat issue trackers were stripped from active UI; the Help menus only point to the BMChat repository for issues.
- The Rust core was rebuilt for Android in WSL Ubuntu 24.04 with Rust 1.91.1 (matching `clients/android/scripts/rust-toolchain`) and Android NDK r25c (`/opt/android/android-ndk-r25c`) via `bash scripts/ndk-make.sh`. The resulting `libnative-utils.so` for `armeabi-v7a`, `arm64-v8a`, `x86`, and `x86_64` is committed in `clients/android/libs/<ABI>/` so APK builds on Windows do not need the native toolchain. The patched core (strict mail filter in `receive_imf.rs`, no-op donation request, BMChat invite host in `qr.rs`/`securejoin.rs`, etc.) is now active inside the APK. We keep the platform-side guard rails as a defence in depth:
  - Android `ConversationListAdapter` filters mailing-list and unencrypted-contact-request chats out of the chat list; `NotificationCenter` skips notifications for those chats.
  - Desktop `QrCode` dialog and shared `util.ts` rewrite legacy invite links (both `i.bmchat.example` and `i.delta.chat`) to `http://5.187.4.132/i#…` and strip the embedded "δ" centerpiece + `get.delta.chat` footer from QR SVGs.
  - iOS `Utils.rewriteInviteLink` / `Utils.stripDeltaBranding` / `Utils.isInviteHost` clean QR SVGs and shared invite URLs and recognise the BMChat IP plus both legacy hosts; `ChatListViewModel` hides mailing-list and unencrypted-contact-request chats; `NotificationManager` suppresses the matching notifications.
  - Android `Util.INVITE_HOST` is now `5.187.4.132` with `LEGACY_INVITE_HOSTS = ["i.bmchat.example", "i.delta.chat"]`; `Util.rewriteInviteLink` rewrites any of these to the canonical BMChat link; `QrShowFragment.fixSVG` strips Delta branding and rewrites copied/shared invite URLs.
  - The yellow "Больше информации" button in the Android login form now opens an in-app dialog with the full provider hint (or generic login help) instead of trying to open `providers.delta.chat`.
  - The `secure_join_wait` device message was rewritten to tell users they can keep writing emails directly if the other side is not on BMChat.
  - Auto-update wiring: `BMChatUpdater` is invoked from `ConversationListActivity.onResume` (post-delayed by 8 s). It checks `http://5.187.4.132/update.json`, compares `versionCode`, downloads the APK to `cacheDir/updates/`, verifies its SHA-256, and triggers the system installer. `network_security_config.xml` whitelists cleartext only for `5.187.4.132`. The user can postpone or permanently dismiss a specific version.
  - VPS layout: the original `/etc/nginx/sites-enabled/nod-tracker` is now split by `infra/vps/deploy.sh` into TWO port-80 server blocks — one with `server_name 5.187.4.132` for BMChat (`/`, `/i`, `/update.json`, `/desktop-update.json`, `/apk/`, `/desktop/`) and another with `server_name mynod.duckdns.org` that keeps the original unconditional `return 301 https://$host$request_uri;`. A pristine copy is kept at `/etc/nginx/backups/nod-tracker.original` so the deploy script can re-patch idempotently without ever breaking the existing nod-tracker frontend on `https://mynod.duckdns.org/`.
  - E-mail-based invites: the QR-show dialog ("Поделиться ссылкой") gained a third action "Отправить на e-mail". On submit BMChat creates (or reuses) a 1:1 chat with the entered address and `dcContext.sendMsg` writes the regular email containing the canonical invite link — the actual transport is the user's own SMTP, no third-party server involved. On the receiver side `BMChatInviteAutoAcceptor` is hooked into `DC_EVENT_INCOMING_MSG`: it scans the message body for a BMChat invite URL (current or legacy host), runs `dcContext.checkQr` and, if it returns `DC_QR_ASK_VERIFYCONTACT/VERIFYGROUP/JOIN_BROADCAST`, calls `dcContext.joinSecurejoin` automatically so the encrypted SecureJoin handshake (also pure e-mail) starts without the user having to tap the link. A short toast confirms the auto-accept.
  - Desktop self-updater: `clients/desktop/packages/target-electron/src/bmchat-updater.ts` runs in the Electron main process. It debounces to once every 12 hours, fetches `http://5.187.4.132/desktop-update.json` via Node's `http` module (Chromium DNS is hard-blocked), compares to `BuildInfo.VERSION` and, if a newer installer is published for the current `process.platform`/`process.arch`, opens a native dialog that links to the installer. The manifest currently advertises the running version so the dialog stays silent until a real installer is uploaded under `/desktop/<arch>/`.
  - Telemetry decoupling: the residual third-party Qualtrics survey URL in `StatsSending.showStatsThanksDialog` was removed; the dialog now just confirms the opt-in. Stats opt-in is kept dormant for future self-hosted use.
  - HTTPS-by-IP redirect: the existing 443 server block on the VPS still has `5.187.4.132` in its `server_name` (next to `mynod.duckdns.org`), so a literal `https://5.187.4.132/i#…` request used to hit the nod-tracker `index.html`. The deploy script now also injects `if ($host = "5.187.4.132") { return 302 http://$host$request_uri; }` at the top of that block — the browser re-attaches the original fragment to the redirect target, so old/cross-platform `https://`-flavoured invite links land on the BMChat invite page instead of NOD.
  - QR landing page: `infra/vps/www/i.html` was rewritten to use canonical `http://` links, surface a "Скопировать ссылку приглашения" button, and trigger an Android `intent://5.187.4.132/i#…#Intent;scheme=http;package=chat.bromore.bmchat.foss;…` so the page transparently hands off to the installed BMChat without the chooser.
  - Onboarding: `WelcomeActivity` no longer steers new users into `InstantOnboardingActivity` (which would have tried a chatmail signup). The primary button now reads "Войти через свою почту" and opens `EditRelayActivity` directly for IMAP/SMTP credentials. The "Альтернативные способы входа" sheet (multi-device, backup) stays.
  - Android updater (full cycle): `BMChatUpdater` re-checks every 30 minutes while the activity is in the foreground (in addition to the 8 s post-launch probe), drives the install through the modern `PackageInstaller` session API instead of `ACTION_VIEW`, requests `USER_ACTION_NOT_REQUIRED` on Android 12+, registers a result-broadcast receiver, and falls back to the legacy `ACTION_VIEW + FileProvider` path if the session API is unavailable.
  - QR sharing as image: `QrShowFragment.shareQrImage()` was added — it renders the BMChat-cleaned SVG to a 1024×1024 PNG, hands it to the share sheet via the existing `${applicationId}.fileprovider`, and a "Отправить QR картинкой" button was added to the share-invite dialog next to the e-mail one (this regression had been silently introduced when the legacy menu entry was dropped).
  - Help content: `clients/android/src/main/assets/help/{ru,en}/help.html` were scrubbed of all "Delta Chat"/"delta.chat" mentions (228 occurrences total). The "Профили из другой установки … Delta Chat недоступны" string in `values-ru/strings.xml` was rewritten in the same spirit.
  - OmniRoute (port 20128) recovery: the BMChat work on port 80 had nothing to do with the actual outage — a stale `sshd` reverse-tunnel forwarder PID had been holding `0.0.0.0:20128` since `May 03 22:08 UTC`, which was making every subsequent `ssh -R 20128:…` from the home PC fail with `Address already in use`. We TERM-killed the orphan and installed `omniroute-port-watchdog.{service,timer}` (cron-style, 1 min) — it auto-evicts any sshd listener on 20128 whose owning ssh session PID is gone, so the home PC's reverse tunnel can reattach without manual intervention. The iptables INPUT rule `ACCEPT tcp dpt:20128` is still rule #1.
  - Android version bump: `clients/android/build.gradle` -> `versionCode 750`, `versionName 2.49.2`. New APK SHA-256 `9e1d980c354c86be5f00412affa024c91b1a8be8ff1e580d688e549ef3ae56d6` (76 442 636 bytes), uploaded as `BMChat-foss-debug-2.49.2.apk` and pointed to by the `BMChat-foss-debug-latest.apk` symlink on the VPS. The previous 2.49.0/2.49.1 APKs are kept on disk so anyone running them gets prompted by `update.json`.
